Инвентаризация скриптов проекта
О документе
Этот файл — черновая инвентаризация скриптов, а не спецификация и не системный промпт. Здесь нет финальных контрактов, схем данных или гарантий полноты. Формулировки вроде «очень важный», «вроде бы используется», «не уверен» отражают текущее состояние понимания на момент написания и являются открытыми вопросами, а не фактами. Многие статусы требуют проверки перед тем, как на них опираться.

Тем не менее общая архитектура и роли скриптов описаны верно: документ даёт представление о том, какие системы существуют, как они сгруппированы и что примерно делают. Его можно использовать как рабочий контекст для генерации нового кода, для рефакторинга и как основу для последующей доработки в полноценный системный промпт.

Правила работы с кодом
Этот раздел задаёт правила для любой работы с кодом проекта: написание новых скриптов, правка существующих, рефакторинг. Раздел не зависит от того, насколько полно описан тот или иной скрипт ниже, и применяется всегда.

Роль и режим работы
Ты работаешь как разработчик этого проекта, а не как автор примера из документации. Это значит: сначала разобраться, как задача решается в существующей архитектуре, потом писать код. Не придумывать новые слои, паттерны и абстракции, если в проекте уже есть подходящие. Не «улучшать» соседний код по ходу дела. Не менять существующие скрипты без явной просьбы, или если только это необходимо — чаще всего новые файлы или точечные правки в тех местах, которые указаны в задаче.

Если из описаний ниже непонятно, как система устроена, или два скрипта выглядят как дубликаты, или статус скрипта помечен как «не уверен», «вроде бы», «возможно не используется», — это повод задать вопрос, а не додумать. В конце ответа с кодом можно указывать блок допущений и открытых вопросов.

Соответствие существующей архитектуре
Новый код должен встраиваться в текущие паттерны, а не заменять их. Конкретно:

Зависимости получать через DI (Zenject) — конструктор, [Inject], инсталлеры. Не использовать FindObjectOfType, GameObject.Find, статические синглтоны и ServiceLocator-подобные решения, даже если в существующем коде так сделано.

Если в проекте уже есть синглтон, который надо задействовать (например, FadeController, HUDController, NightDialogueManager, NoteController, PersistentVolume), — обращаться к нему через существующий интерфейс, но новый аналогичный синглтон не заводить. В новом коде синглтоны не появляются.

Данные — через ScriptableObject, а не через хардкод в компонентах. Если нужны настройки, которые будут меняться геймдизайнером, — это SO в соответствующей папке Data/ или в папке фичи. Если настройки технические и не меняются — [SerializeField] приватные поля.

События — через существующие механизмы (Interactable.onInteraction, TriggerHandler, Unity-ивенты, FMOD-ивенты, WorldFlagEvent, QuestEventBridge, StateEventTrigger). Не изобретать новый event bus, если уже есть подходящий.

Сохранения — через SaveSystem / SaveManager / WorldEventSaver. Новый формат сохранений не вводить. Если новый скрипт должен сохранять состояние, — описать, как он встраивается в существующую SaveData, и явно указать это в ответе.

Сцены — через ScenesManager и LevelLoader, аддитивная загрузка — через AssemblyService как референс. Не грузить сцены напрямую через SceneManager.LoadScene.

Ввод — через PlayerInputManager и PlayerMode. Не читать Input.GetKey напрямую в игровых скриптах, кроме самого PlayerInputManager и UI. Горячие клавиши окон и Esc читает только UIInputHandler, сами окна клавиши не слушают. Режим игрока (PlayerMode) в игре ставит только UIManager: о входе и выходе из фокуса, катсценах, сборке и драге двери ему сообщать (BeginFocus/EndFocus, BeginCutscene/EndCutscene, BeginAssembly/EndAssembly, SetDoorState), а не вызывать PlayerStateController.SetMode напрямую.

Взаимодействие — через Interactable / IFocusable / InteractableView. Новый интерактивный объект наследуется от существующих базовых классов, а не реализует всё с нуля.

Аудио — через AudioService и FMOD EventReference, не через AudioSource.PlayClipAtPoint и не через новые AudioClip-поля, если для этого есть FMOD-ивент.

Всё, что лежит в Deprecated/, не использовать и не наследовать. Не «реанимировать» устаревшие классы — писать новое, только если нет явной просьбы.

Если существующий код в целевом месте сделан неправильно (синглтон, хардкод, захардкоженные ивенты в CleanupManager и т.п.), — не копировать это в новом коде. В ответе указать, что в этом месте есть техдолг, и предложить, как правильно, но не рефакторить старое без запроса.

Стиль кода
Имена классов, методов, полей — на английском, в стиле существующего кода: PascalCase для классов и публичных членов, _camelCase для приватных полей, camelCase для локальных переменных и параметров.

Один класс — один файл, имя файла совпадает с именем класса. Исключения — вложенные приватные типы.

Публичный API — минимальный. Всё, что не нужно снаружи, — private или [SerializeField] private. Не делать поля публичными «на всякий случай».

[SerializeField] private вместо public для полей, которые видны в инспекторе. Валидацию в OnValidate — только если это реально помогает геймдизайнеру.

Никаких public static полей и «глобальных» переменных. Если нужен общий доступ — DI или SO.

Магические числа и строки — в константы, [SerializeField]-поля или SO. Id предметов, квестов, сцен — через существующие ItemDatabase, QuestDatabase, SceneNames.

Не писать код «на будущее»: пустые методы, TODO без контекста, интерфейсы с одной реализацией «на случай, если понадобится». Если функционал не нужен сейчас, — его нет.

Не использовать Region-блоки, если в файле меньше ~400 строк.

Корутины — только там, где уже используется этот подход в проекте (например, ScenesManager). В новом коде предпочитать UniTask / async, если он уже есть в проекте; если нет — уточнить, а не тянуть новую зависимость.

Комментарии и XML-summary
Текущий код в проекте местами перегружен бессмысленными комментариями и одновременно лишён нормальных summary. В новом коде делать наоборот.

Что писать:

XML-summary на все public и protected члены, которые видны за пределами класса: класс, публичные методы, публичные свойства, события, [SerializeField]-поля, которые настраивает геймдизайнер. Одно-два предложения: что делает, какие ключевые ограничения, что бросает или возвращает, если неочевидно.

<summary>, <param>, <returns> — только если без них непонятно. Не расписывать очевидное.

Inline-комментарии — только на почему, а не что. Например: «Прозрачность символов вместо изменения текста, потому что EasyTextEffects ломает альтернативный подход» — хороший комментарий. «Увеличиваем i на 1» — плохой.

Комментарий к неочевидным решениям, обходам багов, работе с движком, шейдерами, таймлайном, FMOD, DI-скоупами. Это самое ценное.

В конце каждого блока с «магией» (аддитивная загрузка сцены, шейдерный фокус, синхронизация с таймлайном) — 1–2 строки, объясняющие, зачем именно так.

Что не писать:

Комментарии-пересказ кода: // применяем урон, // если здоровье <= 0, умираем.

Закомментированный код. Удалять, а не хранить «на всякий случай». История есть в git.

// TODO без контекста, // HACK, // временно без объяснения, что именно сломано и как это чинить.

Комментарии, которые дублируют имя метода или поля.

Комментарии-разделители вида // ===== Methods ===== — если файл маленький, они только мешают.

Личные заметки и обращения к читателю («как я говорил ранее», «не забыть»).

Язык комментариев и summary — русский

Кодировка файлов
Новые файлы — UTF-8 без BOM. Часть старых скриптов лежит в cp1251 (известный случай — StatUI.cs, CRLF, без BOM). Перед правкой существующего файла проверять кодировку и переносы строк, а не полагаться на то, что он в UTF-8: инструменты, которые читают и пишут файл как UTF-8, молча перекодируют русские комментарии. Такие файлы править точечно, с явной кодировкой, и сверять результат по git diff. Если в логе виден mojibake (например «РЎРєРѕР»), кодировка сломана, файл надо переписать правильно.

Что выдавать в ответе
На каждый запрос с кодом — помимо самих файлов:

Что сделано — 2–4 предложения.

Куда положил — путь в целевой структуре папок (см. раздел «Структура папок»).

Кратко, если надо: как встраивается — какие существующие системы использует, что надо забиндить в DI, что повесить в инспекторе.

Что сохраняется — если скрипт должен сохранять состояние, явно указать, как он встраивается в SaveData / WorldEventSaver.

Допущения — что пришлось предположить из-за неполного контекста.

Открытые вопросы — что неясно и требует уточнения.

Техдолг рядом — если в затрагиваемом месте уже есть проблема (синглтон, хардкод, дубликат), отметить, но не чинить.

Не выдавать несколько вариантов «на выбор» без запроса. Не добавлять фичи, о которых не просили. Не менять имена существующих классов и методов, если задача этого прямо не требует.

Core/
Базовые сервисы и системы, от которых зависит остальной проект: сохранения, загрузка сцен, состояние мира, аудио, DI.

Core/Bootstrap/
Скрипты, обеспечивающие начальную инициализацию проекта и предоставление базовых ресурсов через DI.

AssetProviderSOInstaller — хранит префаб игрока, базу данных предметов и квестов, плюс GlobalAudioConfig. Судя по всему, его задача — предоставлять эти ресурсы. Также хранит необязательную базу записок DayNoteDatabase: если поле назначено, она биндится в контейнер, если нет, записки просто не восстанавливаются из сохранения.

Core/State/
Глобальное состояние мира на уровне всей игры.

WorldState — один из самых важных базовых классов. Хранит состояние мира в дневном цикле, работает с флагами, хранит данные о статах, критических статах и пройденном времени. Также содержит логику применения к статам, проверку критичности и работу со штрафом от механики «Глаза». Помимо флагов выбора, в flags лежат служебные флаги вида reward:... — CardManager ставит их как постоянную отметку «награда уже выдана», они сохраняются вместе с остальным WorldState (отдельного формата сохранений для наград нет).

Core/SaveLoad/
Сохранение и загрузка игры, работа с JSON, сохранёнными ивентами и автосохранением.

AutoSaveOnStart — простой скрипт: просто в Start() вызывает сохранение.

SaveLoadBridge — важный скрипт. Висит на сцене как мост для вызова сохранений и загрузок, потому что сам менеджер сохранений находится в ProjectContext. Например, позволяет вызывать сохранение по ивенту.

SaveManager — очень важный базовый скрипт, менеджер сохранений. Связан со многими другими системами, такими как инвентарь (Inventory), WorldState, Quest-система и сам игрок (чтобы сохранить его позицию и т.д.). Знает об игровых сценах, формирует, сохраняет и загружает SaveData. Связан с SaveSystem. Сцену из сохранения LoadGame загружает через SceneTransitionService (то есть через экран загрузки); пока идёт переход, SaveGame и LoadGame игнорируются, чтобы сохранение не записало сцену загрузки как текущую. Id собранных записок пишет в SaveData.savedNotes (берёт из SaveSystem.SessionNoteIds); сами записки при загрузке восстанавливает не SaveManager, а DayNoteManager.

SaveSystem — важный базовый класс. Отвечает за сохранение данных игрока в формате JSON, чтение и загрузку файла сохранения, работу с сохранёнными ивентами. Рядом с SessionTriggeredEvents хранит SessionNoteIds — упорядоченный список id собранных записок (RegisterNote добавляет id без дублей, Load заполняет его из SaveData.savedNotes). Как и события, живёт весь процесс, как именно «Новая игра» его сбрасывает — не проверялось.

WorldEventSaver — очень важный класс, сохранение ивентов и действий, совершённых игроком. Связан с системой сохранений. Id ивента вроде бы генерируется автоматически, но трудно выстраивать сложные цепочки сохранений, хотя возможность удалять ивенты вроде бы это позволяет. Надо будет подумать в будущем, стоит ли его дополнять. В префабах сборки он вешается на объект сокета и связывается UnityEvent'ами: SocketEvent сокета вызывает SaveEventState (id пишется в SaveSystem.SessionTriggeredEvents, то есть в SaveData.triggeredWorldEvents), а в Start при наличии id вызывается onStateRestored, настроенный на AssemblySocket.Apply_now. Apply_now тихий, поэтому восстановленный сокет заполнен только визуально и завершение сборки повторно не запускает. У префабов PortableBase WorldEventSaver нет, их сокеты не сохраняются.

Core/Events/
Обработка событий, привязанных к состоянию мира.

StateEventTrigger — используется для связи принятых решений днём: на основе флагов WorldState и ночного геймплея вызывает ивенты через WorldFlagEvent.

Core/SceneFlow/
Загрузка и выгрузка сцен.

LevelLoader — очень важный класс на сцене: загружает следующий уровень/сцену, может управлять точкой спавна игрока, хоть сейчас это немного не работает. Сейчас в игре некоторые сцены очень тяжёлые, возможно, в будущем придётся его чуть изменить, чтобы он подгружал часть следующей сцены дополнительно. Сам сцену больше не грузит: LoadNext() вызывает SceneTransitionService.TryBegin, и переход идёт через сцену загрузки; если переход уже запущен, повторный вызов сразу выходит, не трогая эссенцию фонарика и PendingSpawn. Поля loadingUI и showUI удалены, экраном загрузки LevelLoader не управляет. Техдолг рядом: в Update остался отладочный вызов LoadNext по клавише P, а поле transition (Animator) не используется.

ScenesManager — общий сервис для загрузки (аддитивно или полностью) и выгрузки сцен. Требует MonoBehaviour-раннер для запуска корутин. Метод BeginLoadSingle(sceneName) начинает полную загрузку с allowSceneActivation = false и возвращает AsyncOperation (null, если сцены нет в Build Settings); активацию разрешает вызывающий код. Используется LoadingScreenController.

SceneNames — хранит Enum названий всех игровых сцен и их игровых названий, даёт к ним доступ. Имя сцены загрузки (Loading = "LoadingScene") задано только константой, в enum GameScene её нет: в инспекторе её выбирать не нужно.

SceneTransitionService — обычный C#-класс, биндится в ServiceInstaller (ProjectContext). Единственная точка запуска перехода через сцену загрузки. TryBegin(targetSceneName) запоминает целевую сцену, взводит флаг IsTransitioning и грузит сцену загрузки; пока переход идёт, повторные вызовы возвращают false. Если сцены загрузки нет в Build Settings, пишет LogError и грузит цель напрямую (без защиты от повторов). Complete() сбрасывает состояние. Используют LevelLoader, SaveManager и LoadingScreenController.

LoadingScreenController — висит на сцене загрузки (LoadingScene, на ней нужен SceneContext). Берёт цель из SceneTransitionService; если цели нет или сцена не загрузилась, пишет LogError и грузит главное меню. Грузит цель через ScenesManager.BeginLoadSingle без активации и плавно заполняет Image.fillAmount. Активацию разрешает, когда progress дошёл до 0.9, бар на 100% и вышло минимальное время показа. Поля в инспекторе: rootCanvas, progressFill, minDisplaySeconds, fillSpeed, holdAtFullSeconds. UI из ProjectContext (HUD, инвентарь и т.д.) не скрывает, а перекрывает канвасом с максимальным sortingOrder. Горячие клавиши (I, Q, N, Esc) на сцене загрузки блокирует UIManager (IsLoading), сам контроллер их не трогает.

Core/Audio/
Общий аудио-сервис и глобальные аудио-настройки.

AudioService — базовый Core-класс. Отвечает за проигрывание звуков в игре, сейчас в основном через FMOD EventReference.

GlobalAudioConfig — не уверен, насколько он нужен; вроде бы для того, чтобы везде был одинаковый звук подбора предмета.

Core/DI/Installers/
Инсталлеры Zenject для сцен и ProjectContext.

DisableInventoryOnStart — инжектит в себя инвентарь на старте и отключает его. Не уверен, насколько это сейчас нужно, но в будущем, наверное, стоит его отключать в определённых сценах и/или моментах.

NoteControllerInstaller — инсталлер для контроллера записок. Не уверен, что корректно работает.

PlayerInstaller — важный инсталлер игрока на сцену, где должен ходить игрок. Например, в дневной сцене игрока нет.

PlayerSubsistemsInstaller — инсталлер подсистем игрока в ProjectContext. Здесь наглядно видно, какие системы присутствуют в глобальном контексте.

ServiceInstaller — тоже инсталлер систем; возможно, нужен, но не уверен, может быть дублирование, хотя вряд ли, скорее нужен. Стоит в будущем проверить. Также биндит SceneTransitionService, UIManager и UIInputHandler.

CleanupManagerInstaller — инсталлер менеджера уборки. Не уверен, насколько он реально нужен.

DayCycle/
Всё, что относится к дневному геймплею: карты, выборы, предупреждения, кризисы, посетители, документы.

DayCycle/Core/
Ядро дневного цикла: контроллер, план дня, механика «Глаза».

DayCycleController — один из самых главных классов, ядро дневного геймплея. Регулирует состояние дневного геймплея, координирует показ посетителей с картами и их диалогами, управляет предупреждениями: карты предупреждения появляются вне очереди, когда стат опускается до нуля. Также была добавлена механика «Глаза», которую мы пока убрали: игрок может нажать на глаз и пропустить текущую карту, но взамен получит штраф на случайный стат. Это нужно, если, например, оба выбора карты заблокированы — такое может случиться, если статы упали до нуля, а выборы должны их понижать. Контроллер также связывает чтение страниц с выдачей наград за страницы (CardPageReward): HandlePageFinished получает индекс прочитанной страницы, а последняя страница приходит без индекса через OnDialogueFinished, поэтому её награда выдаётся там по индексу CardPages.Length - 1. Награда выдаётся до логики промежуточного выбора и до расчёта доступности финального, чтобы выданный предмет мог разблокировать выбор. От повторов при листании назад-вперёд защищает HashSet выданных страниц (grantedPageRewards), он очищается при приходе нового посетителя. Сама выдача делегируется в CardManager.GrantPageReward, контроллер ничего не знает об инвентаре и квестах.

DayPlan — важный ScriptableObject. Нужен для выстраивания последовательности появления карт днём. Например: 3 рандомные, 2 обязательные, 10 рандомных и т.д.

EyeButtonFX — управление UI-эффектами кнопки «Глаза».

EyeFollow — в дневном цикле глаз следит за мышкой.

DayCycle/Cards/
Определения карт и менеджеры, отвечающие за показ и выбор карт.

CardData — ScriptableObject, очень важный скрипт. Содержит базовое определение «карт», которые появляются днём как одна из основных игровых механик. Карта влияет на статы днём (народы, деньги, армия) с помощью выборов Choice: есть left choice и right choice — два выбора, которые по-разному влияют на статы и флаги. Флаги хранятся в целом в мире, в WorldState; флаги определяют, какие карты могут и не могут появиться в дальнейшем. Они также используются, чтобы выстраивать строго определённые или случайные цепочки из карт, благодаря механизмам Required/Block flag add/delete flag. У карты есть текст, тип mandatory или random — используется в DayPlan; также есть вес карты: если она рандомная, вес определяет вероятность выпадения. Есть кулдаун у карты, если она может повторяться; минимальная и максимальная неделя появления; промежуточные выборы (IntermediateChoice): после указанной страницы (triggerAfterPage) показываются два выбора со своими эффектами, флагами, наградами и requiredItem, они применяются так же, как финальные. Награды за страницы лежат в закрытом массиве pageRewards (CardPageReward[]): индекс элемента равен индексу страницы в CardPages, массив может быть короче CardPages или вообще пустым. Доступ только через TryGetPageReward(pageIndex, out reward): метод возвращает false при null-массиве, индексе вне границ, null-элементе и пустой награде, так что рассинхрон длин не даёт исключений и ничего не пишет в консоль. У Choice есть флаг saveGrantStatus (по умолчанию false, чтобы не менять поведение старых карт): если включён, награды выбора выдаются один раз за всю игру.

CardPageReward — сериализуемый класс (не ScriptableObject, лежит в DayCycle/Cards) с наградой за страницу карты: предмет с количеством, квест, записка и флаг saveGrantStatus (для новых наград по умолчанию true). Количество при выдаче приводится минимум к 1, потому что InventoryManager.AddItem молча игнорирует amount <= 0; поэтому это класс, а не struct (у struct новый элемент массива получил бы amount = 0). Награда считается пустой, если не задано ни предмета, ни квеста, ни записки.

CardManager — очень важный скрипт, менеджер карт. Показывает карту, применяет промежуточные выборы IntermediateChoices и окончательный выбор, выдаёт награды выборов и страниц (подробности ниже). Также на карту/просителей в теории можно применять предмет, но сейчас этот функционал устарел, в будущем обновим.

Выдача наград в CardManager (общий путь для наград Choice и наград за страницы): GrantPageReward(card, pageIndex) для страниц и приватный GrantChoiceRewards для выборов; оба сходятся в GrantRewards (предмет через InventoryManager.AddItem, квест через QuestManager.AddQuest, записка через DayNoteManager.AddNote только если HasNote ложно, чтобы не плодить дубли). Если у награды включён saveGrantStatus, перед выдачей проверяется флаг WorldState, а после выдачи он ставится; ключи выводятся из имени ассета карты, без отдельного id: reward:{имя карты}:page:{i} для страниц, reward:{имя карты}:left и :right для финальных выборов, reward:{имя карты}:inter{n}:left и :right для промежуточных (n — позиция в intermediateChoices). Компромисс: переименование ассета карты или перестановка элементов массива меняют ключ и обнуляют историю выдач. Если saveGrantStatus выключен, награда выдаётся при каждом показе карты, как раньше. Требуемый предмет (requiredItem) списывается всегда, независимо от того, выдавалась ли награда раньше: это цена выбора. ResolveIntermediateChoice теперь принимает карту параметром (currData на момент промежуточного выбора указывает на прошлую карту, ShowCard вызывается позже), списывает requiredItem и выдаёт квест, так же как ResolveChoice. Доступность выбора считает CanChoose: недоступен, если нет requiredItem или заблокирован стат.

DeckManager — тоже очень важный класс. Содержит список всех возможных карт и ссылается на состояние мира WorldState. Достаёт подходящую под ограничения карту как mandatory, так и random. Отвечает также за открытие кризисной ветки карт — вроде бы кризис открывается, если стат один или несколько раз полностью понизился до 0.

DayCycle/Choices/
UI и логика выборов игрока.

ChoiceData — ScriptableObject для выбора, не уверен, что используется: всё задаётся в самой карте.

ChoiceHoverHandler — класс для того, чтобы при наведении на выбор показывалось, как выбор повлияет на статы. Механика как из игры Reigns.

ChoiceImpactUI — UI для показа влияния выбора на статы.

ChoiceUI — UI для самих выборов: указываются кнопки выборов, текст, кнопка механики «Глаза». Содержит CardManager и ChoiceImpactUI. Показывает и убирает выборы. Получает InventoryManager через [Inject] и, пока выбор на экране (подписка в Show, отписка в Hide и OnDestroy), слушает OnInventoryChanged: при любом изменении инвентаря (подбор предмета, сборка PortableBase) пересчитывает доступность обеих кнопок через CardManager.CanChoose и обновляет их без участия DayCycleController. Если выбор стал недоступным, прячет панель влияния. Работает и для финальных, и для промежуточных выборов, потому что оба идут через Show.

EffectData — простой ScriptableObject, содержит стат и value, которое к нему применится. Не уверен, что используется.

ImpactIcon — класс для иконки влияния на статы. Заметь: не самой иконки статов, а влияния на конкретный стат. Содержит настройки своего UI и логику анимации.

DayCycle/Warnings/
Система предупреждений, связанных со статами.

WarningConfig — ScriptableObject для предупреждений, связанных с картами и статом.

WarningManager — менеджер предупреждений, важный класс. Обрабатывает поступившие варнинги в очереди; например, если у нас несколько статов одновременно стали критическими (опустились до 0).

DayCycle/Crisis/
Открытие кризисных веток карт.

CrisisManager — очень важный скрипт, менеджер кризисов. Знает о DeckManager и WorldState. Вызывает метод DeckManager.UnlockCrisisBranch для заданного стата, когда надо.

DayCycle/Visitors/
Посетители/просители и их клетка.

CageController — контроллер клетки в дневном цикле, чтобы был цикл: приехала клетка с просителем → показалась его карта → карта завершилась → клетка уехала → цикл повторился.

VisitorController — контроллер посетителей/просителей. Спавнит префаб просителя в клетке, начинает движение прихода и ухода клетки.

VisitorData — ScriptableObject для посетителей: настраивается префаб 3D-модели и звук появления.

DayCycle/Docs/
Механика приходящих и уходящих документов.

DayDialogueManager — менеджер дневного диалога для момента «доков», обрабатывает клик, показ диалогов. Хранит UI и NightTypewriter.

DocsController — контроллер доков. Механика приходящих и уходящих документов как карт. Похож на DayCycleController, обрабатывает показ страниц доков, выбор и диалоги доков, связан с UI доков.

FeatherAnim — скрипт анимации пера для подписания доков. После выбора, сделанного в доках, должна обязательно проиграться эта анимация, и только потом приходит следующий документ.

PageAnim — контроллер анимации страниц доков.

PageController — контроллер страниц, связан с анимациями прихода и ухода страниц.

PageData — содержит текст для диалогов доков.

PagesManager — менеджер страниц доков.

NightCycle/
Всё, что относится к ночному геймплею: сборка, уборка, диалоги, записки, взаимодействия, паззлы.

NightCycle/Assembly/
Механика сборки объектов в отдельной сцене.

AssemblyController — один из самых важных классов. Контроллер режима «сборки», когда игрок не двигается и перед камерой сборочный объект, который можно крутить на WASD, выбирать «сокеты» на нём и заполнять их, собирая тем самым сборочный объект. Отвечает за взаимодействие с объектами сборки и советами, вход и выход из самого режима сборки, инициализацию префаба сборочного объекта. Режим игрока не ставит: этим занимается UIManager через AssemblyService. Завершение сборки приходит из AssemblyView (по событию OnFilled сокета), а не из UI. CompletePendingFills пробрасывает досрочное завершение анимаций заполнения в текущую вью. При открытии сессии PortableBase контроллер сбрасывает уже собранную вью через ResetIfFinished: кэш идёт по префабу, поэтому вторая копия основы получила бы собранную вью. Мировые сборки не сбрасываются. Клик по сокету обрабатывается только в состоянии Empty.

AssemblyGroup — простой класс, который нужен для того, чтобы вызывать Unity-ивент, если мы полностью собрали несколько сборочных объектов.

AssemblyInteractable — висит на сцене на объекте, с которым взаимодействует игрок, чтобы перейти в сборку конкретно для этого AssemblyInteractable, к которому привязан префаб сборки InteractableView.

AssemblyService — координирует открытие и закрытие режима сборки: загружает сцену сборки аддитивно, извлекает AssemblyController, передаёт в него вью и делает сцену активной. Зависит от UIManager: при старте сессии вызывает BeginAssembly(CloseAssembly), при выходе EndAssembly. Для сборки не из PortableBase сначала закрывает текущее окно; при PortableBase инвентарь остаётся открытым под сборкой. Esc, открытие другого окна (I, N, Q), начало катсцены и загрузка сцены завершают сборку через CloseAssembly. CloseAssembly перед выходом мгновенно доводит до конца анимации заполнения сокетов, поэтому любая отмена оставляет согласованное состояние. Повторный вход из цепочки завершения отсекается флагом, чтобы колбэк сборки вызвался один раз.

AssemblySocket — сокет объекта сборки, куда мы вставляем предмет, чтобы заполнить его. Если все сокеты у сборочного объекта заполнены, то он считается собранным. Состояния Empty, Filling, Filled: IsFilled истинно только после завершения анимации, клик и подсветка работают только в Empty. Опциональные поля Fill Animator и Fill State Name задают анимацию прихода part'а: Apply запускает состояние и держит сокет в Filling до его конца, без них сокет заполняется сразу. SocketEvent (звук и сохранение через WorldEventSaver) срабатывает в начале Apply, новый OnFilled — по завершении заполнения, на него подписан AssemblyView. CompleteImmediately мгновенно ставит финальную позу и завершает заполнение (используется при любой отмене). ResetState возвращает сокет в Empty и сбрасывает его сохранённое событие через WorldEventSaver, если тот есть на объекте. Apply_now остался точкой восстановления из WorldEventSaver: заполняет сокет тихо, без SocketEvent, OnFilled и проверки завершения. При отключении в Filling сокет молча переходит в Filled, поза восстанавливается при включении.

AssemblyView — компонент на префабе сборочного объекта. Содержит корневой трансформ для вращения и список сокетов. Наследуется от InteractableView для унификации с другими интерактивными объектами. Подписан на OnFilled своих сокетов и сам вызывает CheckSocketsCompletion, поэтому вставка part'а завершает сборку только после анимации заполнения. CompletePendingFills мгновенно доводит все идущие заполнения до конца, IsLastEmptySocket отвечает, приведёт ли вставка в сокет к завершению сборки, ResetIfFinished сбрасывает собранную вью для новой сессии (частично заполненную не трогает). Слоты в списке могут быть null: в проверках они пропускаются.

LockView — компонент на префабе замка для работы в AssemblyController. Наследуется от InteractableView для унификации с AssemblyView.

Маленький сундук (CHEST_KEY) — собирается в префабе ChestKeyAssemblyRoot: ключ открывает крышку анимацией SmallChest-open, результат — предмет SEVERED_FINGER. Состояние Idle в аниматоре нужно, чтобы ResetIfFinished вернул закрытую крышку для следующей копии сундука. PostWindowDialogue показывает ночной диалог после закрытия всех окон (днём диалога нет). Камера сборки смотрит вдоль +Z, поэтому лицевая сторона модели должна быть развёрнута к ней.

Жаровня с проёмом (NightCycle, Palace/Reliquary/Sword Brazier) — мировая сборка по образцу пьедесталов: в проём в голове статуи вставляется Sword_assembled, меч включается и событие сохраняется. Меши с Outline импортируются с Read/Write, иначе Outline падает при построении нормалей.

Секретный проход из реликвария (Secret path enter) открывается сборкой жаровни или руной на двери, по образцу ENTER_Archive. Руна лежит под дверью через Door rune holder, который гасит масштаб двери, иначе частицы руны искажаются. У двери снят Static, иначе анимация её не двигает.

NightCycle/Cleanup/
Механика уборки объектов и связанные с ней визуальные/звуковые эффекты.

CleanupManager — менеджер для механики уборки, немного не универсальный: в нём захардкожены ивенты, такие как стук в дверь при выполнении стадии, выключение свечей, проигрывание звука бойни и т.д.

CleanupObject — объект уборки. Сейчас используется только актуальный метод CleanWithAnim: проигрывается анимация уборки предмета и звук, в родительской CleanupStage регистрируется факт уборки.

CleanupStage — стадия уборки, простой класс, который хранит счётчик объектов уборки, может вызывать ивент и продвигает стадию в CleanupManager.

Гора трупов в NightCycle (Palace/Hall/Bodies_near_door) — копия из Night1_Final перед дверью кабинета. Пока тела не убраны, дверь заперта LockDoor; после уборки стадия отпирает её и сохраняет событие.

CleanupTrackTarget — висит на телах этой горы: пока идёт уборка, игрок должен вести прицел за телом, увёл — обычный откат. Дальность луча PlayerInteraction на это время растёт, потому что тело уезжает на несколько метров. Сложность — _trackingBoxSize.

CandleController — класс для управления светом и материалом свечей в HomScene, чтобы включать и выключать свечение, мгновенно или со временем.

EyeApparition — глаз без основы в HomScene: появляется за спиной игрока, когда после второго этапа уборки погас свет, и растворяется, когда свет вернулся. Точку ищет на NavMesh вне поля зрения и не в геометрии; если игрок подошёл близко, перелетает.

MusicController — используется в HomScene: проигрывание музыки связано с продвижением по стадиям уборки, управление через FMOD-параметр. Может, можно сделать более универсальным.

NightCycle/Dialogue/
Ночные диалоги и их проигрывание.

DialogueBehaviour — класс для катсцен, проигрывает диалоги в катсценах.

DialogueClip — клип диалога для катсцен, где задаётся текст диалога; связан с DialogueBehaviour.

DialogueGate — новый класс, писал не я. Описание: сначала объект показывает диалог (NightDialogueInteractable), после его прочтения диалог убирается и взаимодействие идёт в обычный Interactable.onInteraction (например, сборка). Повесить Unlock() в NightDialogueInteractable.onDialogueCompleted. Состояние сохраняется через SaveSystem.

DialogueTrack — простой класс, трек диалога на таймлайне.

NightDialogueInteractable — класс, который воспроизводит диалог при взаимодействии с объектом, наследуется от IFocusable.

NightDialogueManager — важный класс, менеджер диалогов ночью, тоже синглтон, надо будет поправить для DI. Принимает страницы диалога, обрабатывает клик мышкой — проигрывает их с помощью TypewriterEffect (важно: именно такое название, а не NightTypewriter; в проекте есть 2 класса, отвечающие за проигрывание текста, возможно, унифицировать в будущем). Также содержит необходимые методы для диалогов в таймлайне.

NightTypewriter — важный класс, который печатает страницы диалога побуквенно, есть возможность скипа. Важно: сейчас это реализовано через изменение прозрачности отдельных символов — так надо потому, что другие методы не очень работают с плагином EasyTextEffects.

NightCycle/Notes/
Записки на уровне и их чтение.

NoteController — тоже синглтон, потом исправить. Важный класс, контроллер «записок» на уровне. Принимает и показывает страницы NoteInteractable, использует UI NoteView, использует NightTypewriter через view. Режим игрока и Esc не обрабатывает: вход и выход из фокуса идут через PlayerInteraction и UIManager.BeginFocus/EndFocus.

NoteInteractable — класс интерактивной записки на сцене, передаёт себя в NoteController, наследуется от IFocusable. При первом фокусе добавляет свою DayNoteData в DayNoteManager (если она задана), а тот регистрирует её id в SaveSystem, так что такая записка тоже сохраняется, если у неё есть id.

NoteView — управляет UI для записок на сцене. Позволяет проигрывать записки как вперёд, так и назад с помощью TypewriterEffect.

NightCycle/Interaction/
Интерактивные объекты ночного геймплея.

CodeLock — класс для кодового замка: содержит комбинацию и дочерние цилиндры. Обрабатывает клик по цилиндрам и проверяет корректность комбинации, может вызывать ивент.

CodeLockCylinder — класс цилиндра кодового замка, хранит текущее значение и метод поворота.

ContInteractGroup — простой класс для отслеживания правильной последовательности взаимодействия с объектами: имеется в виду, что игрок должен провзаимодействовать с объектами в определённом порядке (собрать код), чтобы вызвался ивент.

ContInteractable — простой класс: при взаимодействии добавляет свою часть строки к общему коду; если код уже неправильный, то он обнуляется.

DragDoor — содержит класс PlayerInteractor (видимо, забыл переименовать). Управляет взаимодействием с драггбл-дверьми и заблокированными объектами, также меняет иконку прицела в зависимости от ситуации. Начало драга разрешает UIManager.CanInteract, режим DoorState включается и выключается через UIManager.SetDoorState, а не напрямую.

LockDoor и LockObject — LockDoor наследуется от LockObject. Простые классы, которые говорят PlayerInteractor, что дверь закрыта.

RevealableObject — объект, который невидим и с которым нельзя провзаимодействовать без освещения большей его части светом фонарика. Реализовано с использованием шейдера и отрисовки невидимого конуса освещения фонарика, а не использования самого света фонарика. Rearm снова делает потраченную руну проявляемой: просто включить компонент мало, он помнит «видна» и не включит Interactable, пока фонарь не уйдёт с руны.

NightCycle/Torch/
Факел, который можно снять со стены и носить с собой (сцена NightCycle).

TorchStand — на настенном факеле (префаб InteractiveTorch). Снимается только горящий, после снятия остаётся пустой держатель.

TorchItem — снятый факел (префаб TorchItem): сам считает горение, живёт в руке и на полу. Горит только пока игрок может двигаться; бросок или выпадение отнимают время. Физические коллайдеры на Ignore Raycast, чтобы лучи их не видели, подбор через триггер на корне. Свет свободного факела держится над огнём, чтобы не уходить под пол и за стены.

TorchBurn — обычный класс с правилами выгорания. Погасший факел зажечь заново нельзя.

PlayerTorch — на Player.prefab: подбор, покачивание, бросок на H, замедление игрока, пока факел в руке. Новый факел выбивает старый на пол. Покачивание сделано под руку с весом: восьмёрка в такт шагам с наклоном, наклон при движении вбок, дыхание в покое и отставание от поворота взгляда с пружинным возвратом. Пружина считается мелкими подшагами, иначе при просадке FPS она раскачивается.

TorchFlameWind — отклоняет пламя против движения и держит его вертикально.

Сохраняется только флаг подсказки про H: новая ночь и загрузка возвращают все факелы на стены.

BasePuzzle — базовый класс паззлов, от которого наследуются другие паззлы.

FocusPuzzle — наследник BasePuzzle и IFocusable: паззл, который игрок должен решать в FocusMode.

NightCycle/Puzzles/RotationPuzzle/
Паззл с поворотом объектов на нужный угол.

RotatableItem — поворачиваемый предмет, который нужно повернуть на определённый угол, чтобы продвинуться по паззлу.

SwapItem — предмет для перестановки в паззле.

SwapPuzzle — наследник FocusPuzzle. Мы решаем паззл, когда переставляем swap-объекты в правильные позиции; при этом swap-объекты переставляются по кликам по ним и меняются местами друг с другом. Сейчас, например, у нас это паззл с книгами.

Player/
Всё, что относится к игроку: движение, ввод, взаимодействие, состояние, провайдеры.

Player/Movement/
Движение игрока.

FirstPersonController — очень важный базовый скрипт, контроллер игрока, отвечающий за все виды движения и перемещения. Тряску камеры задаёт через силу и скорость шума Cinemachine отдельно для покоя, ходьбы, приседа и бега; частота покачивания подобрана под интервалы шагов, чтобы шаг совпадал с опусканием головы.

Player/Input/
Обработка ввода игрока.

PlayerInputManager — важный класс для обработки ввода игрока: прыжок, присед, бег, движение, поворот.

Player/Interaction/
Взаимодействие игрока с миром.

PlayerInteraction — скрипт взаимодействия игрока с миром. По сути делает рейкаст и пытается получить Interactable, плюс реализует логику взаимодействия помимо простого вызова ивента. Вход в фокус-объект и выход из него сообщает UIManager (BeginFocus с колбэком ForceExitFocus для Esc и EndFocus), режим игрока сам не ставит. Клавиша E без активного фокус-объекта работает только в режиме свободного движения.

Player/State/
Состояние игрока и мосты для управления им.

PlayerStateBridge — скрипт-мост для взаимодействия с игроком через те же ивенты. Ведь игрока нет на сцене — он спавнится динамически. Позволяет замораживать игрока, отключать/включать системы, перемещать и т.д. SetupToCutscene и SetupFromCutscene вызывают UIManager.BeginCutscene и EndCutscene: окна закрываются, игрок переходит в Frozen. Техдолг рядом: FreezePlayer, SetFocusedMode и SetFreeMode по-прежнему пишут PlayerMode напрямую в обход UIManager (их вызывают события в Memories1 и Night1_Final); их стоит перевести на BeginCutscene/EndCutscene.

PlayerStateController — контроллер состояния игрока, позволяет установить ему PlayerMode. Основной источник режима в игре — UIManager (пересчёт Recompute); прямые вызовы SetMode остались в PlayerStateBridge.

PlayerView — тоже view для получения игрока и связанных с ним систем, но не используется в сцене как PlayerStateBridge.

Player/Providers/
Провайдеры игрока, фонарика и камеры.

CinemachineBrainProvider — вроде как провайдер Cinemachine.

IFlashlightProvider и FlashlightProvider — интерфейс и реализация для получения фонарика игрока.

IPlayerProvider и PlayerProvider — интерфейс и реализация провайдера игрока (Player/PlayerView).

Inventory/
Инвентарь и предметы в нём.

InventoryManager — менеджер инвентаря, инжектит базу данных предметов. Добавляет предметы и удаляет. В него загружаются и из него сохраняются предметы. Событие OnInventoryChanged приходит на любой AddItem, RemoveItem и ReplaceItem; на него подписаны InventoryUI, DayItemHints и ChoiceUI. ReplaceItem(old, new) атомарно меняет один экземпляр предмета с единственным событием: результат встаёт на позицию старого предмета, если тот был единственным, иначе добавляется в конец. Сборка PortableBase использует именно его, поэтому подмена — одно событие, а не Remove + Add.

InventoryUI — один из самых важных и сложных классов. Это UI инвентаря. Есть несколько типов предметов: normal, part, portable base и static base (вроде не используется — это статичный объект сборки на ночной сцене). Part показывается в главной панели наравне с Normal и PortableBase и по клику ведёт себя как Normal; деталью он остаётся в мини-панели сокета, которая собирается отдельно по клику по сокету и показывает все Part-предметы инвентаря. Portable base-предметы — предметы с механикой сборки, которые мы можем открывать прямо в инвентаре и собирать их из part-предметов; когда соберём — это считается уже другим предметом. Выбор Normal или Part закрывает активную сессию сборки и на этом заканчивается; выбор PortableBase закрывает предыдущую сессию и открывает новую. Реализует IUIScreen и сам регистрируется в UIManager (screenId — ассет Inventory, клавиша I); Open и Close вызывает UIManager, клавиши инвентарь не читает. Close завершает активную сессию сборки, поэтому закрытие инвентаря (Esc, I, N, Q) закрывает и сборку PortableBase. Публичный Toggle() оставлен для UnityEvent в сценах и делегирует в UIManager. Техдолг рядом: при открытии автоматически выбирается последний предмет, и если это PortableBase, сборка стартует сама. Если в сцене лежит свой экземпляр InventoryUI без screenId (так было в DayCycle и Memories1), он даёт ошибку регистрации: настоящий экземпляр создаёт PlayerSubsistemsInstaller в ProjectContext. Сборка PortableBase: инвентарь заменяет основу на результат сборки в момент вставки последней детали, до запуска анимации сокета, одним вызовом InventoryManager.ReplaceItem. Пока играет финальная анимация, слот заморожен: показывает старый предмет с прежним выделением, а RefreshUI подставляет старый предмет на место результата. По завершении анимации колбэк снимает заморозку, слот обновляется на месте через ItemSlot.Set и выделение переходит на результат. При любой отмене (Esc, закрытие инвентаря, смена предмета, меню, катсцена) заморозка снимается сразу, поэтому состояние всегда согласовано; Open и Close снимают её перестраховочно. Слоты главной панели переиспользуются по индексу и обновляются только при смене предмета, без Destroy и Instantiate. Заморозка не включается, если копий основы больше одной, результат уже есть в инвентаре или он не показывается в главной панели — тогда слот обновляется мгновенно. При пустом resultItem подмены нет, и сборка завершается без изменений инвентаря.

ItemSlot — слот для предмета, в котором отображается предмет в инвентаре. Сейчас неоптимизированно: для каждого предмета создаётся отдельная камера и источник освещения, чтобы рендерить его 3D-префаб в иконку в инвентаре. Желательно в будущем настроить переиспользование, но и добавить возможность кастомной настройки освещения/яркости предметов, при этом используя один источник освещения и одну камеру; нужно продумать, возможно ли это вообще. Поле icon не используется: иконка рисуется из uiModelPrefab, поэтому предмету без модели соответствует пустое превью. Геттер Item отдаёт текущий предмет слота, по нему InventoryUI понимает, нужно ли обновлять слот.

PickupItem — простой класс для подбора предмета в инвентарь, а также для удаления предмета из инвентаря.

UI/
Общий интерфейс: менеджер окон, HUD, статы, меню, фейды, подсказки, тултипы.

UI/Manager/
Централизованное управление окнами, блокировками ввода и режимом игрока.

UIManager — очень важный класс, обычный C#-класс в ProjectContext (биндится в ServiceInstaller). Держит единственное открытое окно и контексты: катсцена, сборка, фокус-объект, драг двери. Режим игрока пересчитывается из состояния целиком и ставится только здесь, поэтому закрытие одного окна не перебивает режим, которого требует другой контекст. Окна работают как вкладки: Open закрывает текущее окно и прерывает сборку, Toggle закрывает открытое окно или открывает новое. Esc (HandleCancel) делает одно действие за нажатие: если идёт сборка, закрывает окно и сборку целиком, игрок сразу в свободном движении; иначе закрывает окно; иначе выходит из фокус-объекта; иначе открывает окно паузы (UIScreenId с IsPauseMenu). Пока открыто окно паузы, другие окна не открываются. Открытие окон запрещают загрузка сцены, катсцена, активный фокус-объект и блокировки (BlockAll/UnblockAll, учёт по владельцу). Скрытие оверлеев — HideAll/ShowAll, тоже по владельцу. Режим катсцены задан константой CutsceneMode (сейчас Frozen). При смене сцены в режиме Single состояние сбрасывается, колбэки отмены при этом не вызываются.

UIInputHandler — ITickable, единственное место, где читаются Esc и хоткеи окон (клавиша берётся из UIScreenId.ToggleKey).

UIScreenId — ScriptableObject-идентификатор окна: клавиша открытия и флаг IsPauseMenu. Ассеты лежат в Assets/Configs/UIScreens (Inventory, Quests, Notes, Settings) и назначаются в поле Screen Id у окна. Без ассета окно не регистрируется, в консоль пишется ошибка.

UIBridge — мост сцены к UIManager для UnityEvent и инспектора: ToggleScreen, OpenScreen, CloseScreen (с ассетом UIScreenId), CloseCurrent, BlockAll/UnblockAll, HideAll/ShowAll, BeginCutscene/EndCutscene. При уничтожении снимает свои блокировки и скрытия.

UIHideableGroup — вешается на корень оверлея с CanvasGroup (HUD, подсказки, фонарик), регистрируется в UIManager и прячется по HideAll (альфа 0 и без raycast), не отключая объект. Не уверен, на какие префабы он уже повешен: проверить.

BridgeUI — лежит в Day_notes. Старый мост блокировки окон, оставлен под прежним именем ради сцен (например, Memories1), теперь делегирует в UIManager.BlockAll и UnblockAll.

К UIManager подключены окна InventoryUI, QuestUI, SettingsMenu и DayNoteUI (журнал записок, лежит в Day_notes, screenId — ассет Notes). Публичный Toggle() у окон оставлен для старых UnityEvent и делегирует в UIManager.

Записки (папка Day_notes): DayNoteData — ScriptableObject записки (страницы, название, иконка) с полем id для сохранений; без id записка не восстанавливается после загрузки. DayNoteDatabase — ScriptableObject-база всех записок по образцу ItemDatabase и QuestDatabase (GetNoteById), назначается в AssetProviderSOInstaller. DayNoteManager — MonoBehaviour на сцене со списком записок; через [Inject] получает SaveSystem и DayNoteDatabase (оба необязательные), при инъекции восстанавливает записки из SaveSystem.SessionNoteIds, а AddNote регистрирует id записки в SaveSystem. Поэтому записки с id теперь переживают смену сцен в рамках сессии и загрузку сохранения. DayNoteUI после подписки на OnNotesChanged вызывает Refresh, чтобы показать записки, восстановленные до подписки.

UI/HUD/

HUDController — важный класс, контроллер прицела игрока: изменяет размер, иконку прицела, включает и выключает текст взаимодействия с предметом. Важно: это синглтон, надо будет переписать под Zenject.

World/
Объекты мира и окружения, не привязанные жёстко к дневному или ночному циклу: триггеры, двери, свет, телепорты, VFX, AI.

World/Environment/
Скрипты для визуального и звукового поведения окружения.

AnimDesynch — рассинхронизация воспроизведения анимаций.

AnimRewind — визуальный откат анимаций. Используется, например, в новой механике уборки: если игрок зажал взаимодействие, но отпустил кнопку, тем самым не додержав, проигрывается откат анимации уборки, и он должен сделать всё сначала.

CutsceneSkipper — код писал не я. Класс для пропуска катсцен на пробел с сохранением всех ивентов/сигналов. Возможно, не оптимизирован — в будущем посмотреть.

EyeConstraint — это уже глаза на ночной сцене: просто механика, что есть 3D-модели глаза, которые смотрят в направлении игрока. Цель — камера (Camera.main). Используется также на костях Head статуй Office 1–8 в StaticStatues.

HallGuide — новый класс, писал не я. Вроде отвечает за последовательность включения света в зависимости от «шагов» игрока. Не оптимизирован — возможно, исправить. Запускается руной у двери в спальню. `finalObjects` (боковые лестницы) включаются вместе с остальным светом, `finalRemovedObjects` (балюстрады в их проёмах) в этот момент выключаются.

RendererDissolve (`NightCycle/Interaction/`) — растворение меша на шейдере `QMD/BalustradeDissolve`. Длительность должна совпадать с Delay у Interactable руны.

DissolveAppear (`NightCycle/Interaction/`) — проявление выключенного объекта обратным растворением: на время подменяет материалы на варианты `*_Dissolve` по списку пар. Новый материал на объекте нужно добавить в список.

FogFollower (`Visual/`) — плавно ведёт туман за персонажем (призрак Александра). Может быть дочерним объектом персонажа: позицию считает в мировых координатах.

ParticleFadeOut (`NightCycle/Interaction/`) — плавно гасит частицы и звук, затем выключает объект.

IconTurnOn — плавное включение/выключение иконок статов (ну и просто картинок).

OfficeBlackout — новый класс, писал не я. Нужен для одного эпизода в ночной сцене; в будущем оптимизировать и сделать универсальным.

StatueBreath — скрипт для «дыхания статуй ночью». По факту достаточно универсален: проигрывает звук и после проигрывания вызывает Unity-ивент.

World/Triggers/
Триггеры и обработка входа игрока в зону.

TimedPlayerTrigger — класс, чтобы вызывать ивент, если игрок достаточно долго простоял в коллайдере; при выходе сбрасывается таймер.

TriggerHandler — класс, чтобы вызывать ивент, когда игрок входит в триггер.

World/Doors/
Двери и их поведение.

DoorCloser — скрипт для закрывания двери за игроком, а также блокирования/разблокирования двери.

HoldDoor — дверь на удержании E (префаб HOLD_DOOR), на неё переведены одностворчатые двери; двустворчатые по решению автора остаются старыми (старые префабы — в Interactive Door OLD). Pivot створки на оси петель. При прерывании дверь замирает, прогресс не сбрасывается; реверса на полпути нет, створка уходит от игрока. Если рядом висит запертый LockObject, взаимодействие выключено до Unlock. OpenAutomatically заменяет DoorCloser.OpenDoorEvent. Состояние не сохраняется. Статуя, идущая через проём, вызывает TryKick: дверь резко распахивается от неё до конца, в том числе перекидываясь через закрытое положение, и отталкивает игрока со своего пути; запертые двери держатся, а их NavMeshObstacle вырезает проём из навмеша, пока замок закрыт, чтобы статуи искали обход.

SecretPassageDoor — висит на стенах-дверях ENTER_Archive и ENTER_Library в NightCycle. Помещения за ними (Palace/Archive и Palace/King Block с телепортом в библиотеку) выключены, пока их не включит руна или телепорт в архив: это экономит отрисовку, occlusion culling в сцене не запечён. Выход ловят два TriggerHandler внутри помещения: триггер у двери изнутри взводит триггер в холле, тот вызывает Close — дверь закрывается обратным клипом (состояние close в контроллере), после клипа помещение выключается, а руна снова становится активируемой. Close сбрасывает триггер play, потому что рычаг архива ставит его и при открытой двери. Рычаг (Archive/Lever) тоже снова включается после закрытия; при загрузке он остаётся рабочим, потому что дверь архива после загрузки всегда закрыта. Событие руны библиотеки значит «проход открыт»: при загрузке OpenImmediately ставит дверь открытой и включает King Block (игрок возвращается из Library внутрь комнаты), при закрытии событие стирается. Гул руны (`_runeHum`) затухает, когда дверь доиграла открытие, и включается снова после закрытия. Конец открытия ловится по состоянию аниматора, а не событием клипа: клип Library enter используется и в King block Day, где событию не нашлось бы получателя.

Луч PlayerInteraction пропускает триггеры без тега Interactable (Volume, чекпоинты), иначе они закрывают двери и предметы за собой.

Стена холла SM_Wall_E (1) односторонняя: со стороны проёма капсула игрока застревает в её толще. У дверей в такой стене ставить невидимый Doorway Filler (BoxCollider, слой Environment).

World/Lights/
Управление светом.

LightController — плавное включение и выключение и изменение яркости источников света с запоминанием оригинальной яркости.

DarknessZone — объём-триггер (слой Ignore Raycast, чтобы не перехватывать луч взаимодействия), в котором огни с FireDarkness гаснут и разгораются: Darken и Restore вызывают те же события, что гасят свет помещения. В NightCycle это Office Darkness Zone: её вызывают OfficeBlackout (подбор статуэтки) и Atack trigger статуй кабинета вместе с LightController.

World/Teleport/
Телепорты и управление точкой спавна.

DelayedTeleport — телепорт игрока в точку на сцене с задержкой.

PendingSpawn — вроде используется для кастомного спавна, но не уверен. Кстати, оригинальная точка спавна задаётся в PlayerInstaller при спавне игрока, но иногда её надо поменять на кастомную, например при переходе между сценами.

SeamlessTeleporter — бесшовный телепорт игрока в одинаковые помещения. Используется в Night1_final для создания эффекта бесконечной лестницы с дверьми.

World/VFX/
Визуальные эффекты.

VFXFadeController — используется на Particle System-объектах, чтобы настроить кастомную анимацию исчезновения, например при подборе «эссенции» для фонаря.

FireIgnition — новый класс, писал не я. Используется для разгорания и затухания «огня»: свет, emission и частицы, дым. SetBurnLevel задаёт уровень огня для выгорающего факела. SetDarkness — внешнее затемнение поверх горения: умножает свет и свечение, при полной темноте прячет пламя и не меняет IsLit.

FireDarkness — универсальный компонент на любом огне с FireIgnition (стоит в префабах InteractiveTorch и TorchItem): каждый кадр ищет DarknessZone по своей позиции, поэтому факел гаснет и на стене, и в руке, и на полу.

World/AI/
Искусственный интеллект врагов.

NavigationController — важный класс для врагов, использует NavMesh для движения к игроку. В будущем надо будет точно доделать. Каждый кадр ищет на слое DoorLayer двери HoldDoor рядом и передаёт им своё направление движения, чтобы статуи выбивали двери; направление берётся по фактическому смещению, потому что на NavMeshLink скорость агента не отражает движение. Через проём спальни, где навмеш разорван створкой при запекании, статуи проходят по Bedroom Door NavLink.

Data/
ScriptableObject-данные, которые читаются несколькими системами.

Data/Items/
Данные предметов.

ItemData — ScriptableObject игрового предмета. Содержит тип предмета, 3D-модель префаба для рендера как объёмной иконки в инвентаре, а также префаб сборки, если это PortableBase, и resultItem — предмет, которым основа становится после сборки. Пустой resultItem означает, что сборка завершится без подмены предмета. Сборка PortableBase заменяет предмет через InventoryManager.ReplaceItem, поэтому результат должен иметь непустой id и лежать в ItemDatabase: иначе он не сохранится и не восстановится после загрузки.

ItemDatabase — база данных предметов, которая содержит в себе все предметы. Нужна для получения предмета по его id, связана с системой сохранений.

Data/Quests/
Данные квестов.

Quest — ScriptableObject квеста, содержит в себе список QuestStage, по которым нужно продвигаться.

QuestDatabase — ScriptableObject-база данных всех квестов: получение квеста по id.

Data/Stats/
Визуальные данные статов и их изменений.

StatImpactVisualData — данные по иконкам влияния: настраиваются спрайты для каждого типа влияния.

StatVisualData — ScriptableObject визуальных данных статов.

Data/UI/
Данные общих UI-компонентов.

DrumCounterSettings — ScriptableObject настроек DrumCounter: скорость, сглаживание и выброс за цель. Один ассет на все счётчики (Assets/Configs/Ui_Drum_Configs), чтобы они крутились одинаково.

Shared/
Общие интерфейсы, перечисления и утилиты, которые используются в нескольких фичах.

Shared/Interfaces/
Базовые интерфейсы.

IFocusable — важный базовый интерфейс для всех focus-объектов: это такие объекты, при взаимодействии с которыми игрок переходит в FocusMode, то есть фризится и включается курсор.

IUIScreen — интерфейс окна под управлением UIManager: Id (UIScreenId), Open и Close. Окно регистрируется само в [Inject]-методе через UIManager.Register; Open и Close вызывает только UIManager.

IUIHideable — интерфейс оверлея, который прячется через UIManager.HideAll: единственный метод SetHidden(bool). Реализует UIHideableGroup.

Shared/Interaction/
Базовые классы интерактивных объектов.

Interactable — очень важный класс для всех Interactable-объектов. Содержит ивент, который вызывается при завершении взаимодействия; несколько типов взаимодействия — мгновенное по нажатию кнопки и по зажатию и удержанию кнопки.

Outline (QuickOutline) красит все рендереры своей иерархии, поэтому огонь и частицы держать рядом с моделью, а не внутри неё (так сделаны факелы и жаровня с мечом).

InteractableView — базовый класс для всех интерактивных объектов сборки, которые спавнятся в AssemblyController. Определяет общий интерфейс для вращения и событий.

Shared/Enums/
Перечисления, общие для нескольких систем.

PlayerMode — enum состояний игрока: фокус, свободное движение и состояния взаимодействия с драггбл-дверью (свободное движение, но без вращения камеры). Также есть Frozen: движение и поворот выключены, курсор скрыт; используется в катсценах (UIManager.CutsceneMode).

Shared/UI/
Общие UI-компоненты.

TypewriterEffect — скрипт для печати текста в диалоговом окне. Страницы диалога можно скипать, листать и возвращаться назад по ним. Тот же механизм с прозрачностью букв. Важная деталь для потребителей событий: OnPageFinished(pageIndex) приходит для всех страниц, кроме последней, а для последней вместо него приходит OnDialogueFinished без индекса; Skip и естественное окончание печати вызывают те же события. Страница, показанная повторно (после «назад»), печатается мгновенно и снова поднимает то же событие, поэтому подписчики, которым нужна однократность (например, награды за страницы в DayCycleController), должны защищаться от повторов сами. Скрипт общий для диалогов, записок и документов, поэтому его поведение лучше не менять ради одной фичи.

DrumCounter — счётчик целых чисел с прокруткой барабана (одометр), partial-класс из DrumCounter.cs и DrumCounter.Rolling.cs. Ничего не знает про StatUI, в DI не регистрируется, API один — SetValue(int, bool animate). Template — дочерний TMP, с которого клонируются цифры; после сборки он выключается, поэтому делить один шаблон между счётчиками нельзя. Значение больше ёмкости Max Digits обрезается. Allow Negative не проверялся.
